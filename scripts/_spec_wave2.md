## 批 2：问答统一信封 + 未命中如实说

**目标**：问答返回统一结构，未命中必须如实说，禁止编造。

**允许改**：`codes/ontology_qa_v3.py`、`codes/ask_service.py`、`codes/evidence.py`；新增 `scripts/verify_qa_envelope.py`；报告 `docs/实验/问答信封与未命中-20260924.md`。

**要求**
1. 统一返回信封：`{answer, hit: bool, reason, evidence[], advisory?}`；所有分支都必须带 `hit`。
2. `hit=false` 时 `answer` 明示"未命中"并给 `reason`（如"无可靠依据"），**不得回填任何推测内容**。
3. 每条 `evidence` 必须可回溯：`{kind: entity|relation|dict|doc, id, label, source}`。
4. 保持向后兼容：老字段不删（新增字段优先），前端现有读取不能坏。
5. 自检（终端真跑）：① 有答案问题 `hit=true` 且有 evidence；② **无答案类问题 `hit=false` 且 answer 不含编造事实**（批 1 评测集里"无答案类"要零编造）；③ 跑批 1 的 `scripts/eval_qa.py`，**命中率不降、误答率下降或持平**，前后数字并列贴出。

**门**：命中率不降 + 无答案类零编造 + 老字段仍在。

## 批 3：模型建议层（可选适配）

**目标**：模型只出候选与依据，绝不充当结论。

**允许改**：新增 `codes/model_advisory.py`；接线最小改 `codes/ask_service.py`；新增 `scripts/verify_advisory.py`；报告 `docs/实验/模型建议层-20260924.md`。

**要求**
1. 适配器模式：未配置模型（无 key/env）时**完全不启用**，行为与批 2 逐字段一致。
2. 启用时输出只能进 `advisory`：`{candidates:[], basis:[], model:"..."}`；`hit` 仍按批 2 判定（模型命中**不算** `hit=true`）。
3. 界面上（若涉及）候选必须标"建议候选，需人工确认"。
4. 自检：① 无模型时，对同一批问题逐字段比对批 2 输出（一致率 100%）；② 有模型时（可用假适配器或本地小模型）`hit` 判定不被模型影响；③ 断言 `advisory` 不进入 `answer`。

**门**：无模型时行为零变化（可回归证明）。

## 批 4b：编排上半截（流程定义 + 控制流 + 预设）

**目标**：能定义并运行带控制流的流程；**不新增执行体系**，复用插件框架与事件总线。

**允许新增**：`codes/flows/`、`codes/flow_engine.py`、`codes/flows/*.json`、`scripts/verify_flows.py`、报告 `docs/实验/编排上半截-20260924.md`；接线最小改 `codes/api_server.py`（只加只读/触发路由）。

**要求**
1. 流程定义 JSON：`{flow_id, name, steps[], edges[], preset?}`，风格与 `plugin_framework` 的 manifest 一致。
2. 步骤引用**已有能力**或插件扩展点，经 `reg.call(kind, id, params)` 执行。
3. 控制流四件：`parallel`（同列并行）、`branch`（条件分支）、`loop`（带出口条件）、`gate`（按上游证据判放行/打回，回哪一步在定义里可见）。
4. 每步结果写 `event_bus`，全过程落 `audit_chain`，可按时间线回放。
5. 失败**如实写原因并停在该步**；上游无输入写"没有输入"，**不判整条失败**。
6. 预设卡放配置而非代码；`preset:true` 的流程可被列出并一键触发。
7. 只做**通用流程引擎**，不含行业口径与甲方业务规则。

**门**：① 一条 5 步流程（含并行 + 门控）跑通并有事件流；② 门控打回能回到指定上游步；③ 流程加载失败在接口写出真实原因；④ 预设与流程定义一一对应。
