# factory-ontology × opa-monitor 本体建模能力对齐与舆情系统优化建议

> 目的：把「本体驱动问答系统 factory-ontology」与「本体驱动舆情监控 opa-monitor」在本体建模技术能力上做一次系统对齐，找出舆情系统可借鉴/可优化的点。
> 方法：两仓库真实代码盘点 + 建模引擎能力对照，非臆断。日期 2026-09-03。

## 〇、一句话结论

两个系统共用同一套本体世界观（CSV→本体→规则/图谱→问答），但**本体建模引擎处在两代**：
- **factory-ontology** 已演进到「suggest_schema 自动推断 + validate 约束 + 词典lexicon 自动生成 + to_nt 统一导出」的**第二代自动建模**（schema_ontology.py 849 行）；
- **opa-monitor** 仍停留在「手工维护 industry_schema.json + 复用早期 csv_to_owl.py(120行) 出 .nt」的**第一代半自动建模**，且**硬编码依赖父仓库路径**。

舆情系统不是"建模能力缺失"，而是"建模引擎没跟上第二代码"——它的 schema 声明(类型层级/对象关系)其实已在，缺的是**自动推断、约束校验、词典统一、关系自动挖掘**这四件工厂本体已经有的东西。

## 一、两系统本体建模引擎现状（真实代码盘点）

### A. factory-ontology（第二代，自动建模）
载体：`codes/schema_ontology.py`（849 行），配套 lexicon*.json 词典、ontology_schema.json。

| 能力 | 函数 | 说明 |
|---|---|---|
| Schema 自动推断 | `suggest_schema(data)` L554 | 从 CSV 列名/值自动推断 schema，无需人画 ER 图 |
| 属性语义角色 | `classify_properties` L114 / `_infer_prop_role` L94 | identifier/measure/category/ref 角色归类 |
| 类型体系 | `build_class_hierarchy` L126 | 自动建类层级 |
| 关系推断(规则) | `_infer_relations` L243 | 主键/外键启发式推断对象关系 |
| 关系推断(LLM) | `_infer_relations_llm` L355 | LLM 辅助补关系，可关闭 |
| 约束校验 | `validate` L672 | 结构约束检查 |
| 词典 | lexicon.json | 中文映射/枚举/同义词 外置 |
| 统一导出 | `to_nt` L849 | 数据/类/关系/实例统一 N-Triples |
| 图谱 | `build_graph` L595 | 对象关系图 |

### B. opa-monitor（第一代，手工 schema + 半自动）
载体：`modules/ontology_build.py`(29行, 硬编码调 `../../ontology-analysis/src/csv_to_owl.py`) + `config/industry_schema.json`(手工)。

| 能力 | 载体 | 说明 |
|---|---|---|
| 母本体构建 | ontology_build.build_mother | subprocess 调**外部旧 csv_to_owl**(120行纯数据属性) |
| Schema 声明 | industry_schema.json | **手工**写 table/type_hierarchy/object_relations |
| 类型层级 | type_hierarchy | 手工声明(整车/动力电池/...) |
| 对象关系 | object_relations | 手工声明(suppliedBy/locatedIn/partOf) |
| 深关联传导 | ontology_enhance.build_conduction_graph | 事件匹配后的图传导 |
| 二次建模 | second_modeling | 事件子图生成(事件=新维度实例) |
| 词典 | 无独立 lexicon | 靠 sentiment 词典 + event_extract 规则词 |

## 二、核心对齐差异（factory-ontology 领先什么）

| 维度 | factory-ontology | opa-monitor | 舆情可借鉴 |
|---|---|---|---|
| Schema 来源 | **自动推断**(suggest_schema) | 手工维护 json | ✅ 建新行业时省人工 |
| 关系挖掘 | 规则+LLM 自动推断 | 手工声明 object_relations | ✅ 关系漏配可补 |
| 词典 | 独立 lexicon, 中文/枚举/同义词外置 | 无统一词典, 散在代码 | ✅ 词典统一化 |
| 约束校验 | validate() 结构检查 | 无(手工保证) | ✅ 建模错误早发现 |
| .nt 导出 | to_nt 统一(新版 csv_to_owl 181行含对象属性) | 复用旧 120行(无对象属性) | ✅ 关系进 .nt |
| 引擎路径 | 仓库内自洽 | **硬编码跨仓库路径** | 🔴 耦合父仓库, 易碎 |
| 泛化 | 18+行业实测 | 2 行业 schema | 对齐多行业 |

## 三、舆情系统优化建议（按 P 级）

### P0（正确性/结构风险）
1. **🔴 硬编码父仓库路径**：`ontology_build.py` 写死 `D:/ontology-analysis/src/csv_to_owl.py`。若该目录不存在/改名 → 母本体构建崩。建议：把新版 csv_to_owl.py(181行) 拷进 opa-monitor 本地 or 统一走 factory-ontology 引擎。**舆情不应依赖它管不到的旧仓库路径**。

### P1（能力对齐，直接借用工厂本体已验证能力）
2. **母本体 .nt 用旧 csv_to_owl(120行纯数据属性)出，但对象关系由 enhance() 事后补**——两步走可合并成 factory-ontology 的 to_nt 一步(新版 csv_to_owl 181行支持 --relations 直接输出对象属性声明，含 domain/range)。减少两套写入路径。
3. **用 suggest_schema 自动推断辅助/校验手工 schema**：schema 的 object_relations.node_col 需与 CSV 真实列名精确一致(如 partOf 配 parent_product 列但 CSV 无此列 → 静默 0 关系)。可用 suggest_schema/关系推断在 CSV 上跑出候选关系做交叉核对，防漏配/错配。
4. **validate 建模校验门**：industry_schema.json 的 node_col/type_col 引用的列在 CSV 里不存在时，build 前报错而非静默空(partOf→parent_product 缺失列即实例，传了 0 关系但没警告)。type_col 值不在 type_hierarchy 里也应提示。
5. **词典统一化**：event_extract 关键词/sentiment 负面词收进独立 lexicon，与 factory-ontology 换行业只换词典的纪律对齐。

### P2（工程卫生）
6. 文档标注 opa-monitor 与 factory-ontology/ontology-analysis 继承关系，避免双仓库建模引擎漂移。
7. 深关联传导的 node_importance/conduction_weak_factor 等风险参数可考虑由 factory-ontology 的 schema 语义角色(measure/category)联动, 减少手工调。

## 四、实测确认结论（跑真数据核对，非臆断）

对最初存疑的三点做了**真实链路验证**(enhance_triples + build_conduction_graph 实际执行)：
1. **母本体 .nt 有对象关系**：mother.nt 含 20 条 suppliedBy/locatedIn 关系三元组(非纯数据属性)。✅ 传导图有 10 节点且有邻居，深关联传导**工作正常**。
2. **对象关系来源**：由 enhance()/enhance_triples 从 CSV+industry_schema.json 现算后**追加**进 .nt，再被 build_conduction_graph 读入建图。是"旧 csv_to_owl 出数据属性 + enhance 补对象关系"两步走。
3. **发现一个真实建模隐患**：schema partOf 的 node_col=`parent_product` 但 **CSV 无此列**(有 production_line/supplier 等) → partOf 静默生成 0 关系，无任何警告。validate 校验门可拦这种错配。
