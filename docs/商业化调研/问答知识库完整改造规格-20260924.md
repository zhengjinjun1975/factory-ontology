# 工厂本体问答知识库 完整改造规格（保持开源）

## 〇、一句话

对**问答知识库**做一轮完整改造：把问答引擎从"规则命中"升到"本体约束 + 模型建议 + 人在环"，把多行业/多知识库从"一库一改"升到"注册表驱动"，把商用级加固（鉴权 fail-closed、并发、离线部署）补齐；**改造只落开源轨道，闭源轨道的编排/交付/行业流程一律不进本库**。

## 二、编排边界（2026-09-24 按代码实核，纠正前版臆断）

**前一版这段是错的**：我写了"编排、九行业口径、人在环留闭源"，那是照抄技能里的旧路径（`factory-ontology-kit`、`E:/ontology-delivery-tool` 本机已不存在），**没有去代码里核**。按实际代码，情况如下：

**开源库已有的（实查）**
- `codes/plugin_framework.py`（706 行）：插件框架。清单 `manifest.json`（name/kind/version/entry/provides）、生命周期 `load → register → run → unload`、扩展点注册表 `(kind, id) → handler`，对外 `reg.call(kind, id, params)`。→ 这是**原子装配 + 能力注册与路由**那一层。
- `codes/event_bus.py`（324 行）：事件总线，事件驱动。→ 这是**事件账本/触发**那一层。
- `codes/core/base_agent.py`（67 行）+ `codes/agents/`（query / eval / lexicon 三个 agent）。→ 智能体基类与具体智能体。
- `codes/mcp_server.py`：对外能力暴露。

**开源库没查到的**
- **任务级编排**：把多个原子串成一条带**并行 / 分支 / 循环 / 门控**的流程，以及"预设卡"那种一键跑整套编排的形态，本库里没有（`grep chain/flow/preset/pipeline` 命中的是 `audit_chain.py` 审计链，不是编排）。

**结论**：本体库有**编排骨架的下半截**（原子、能力路由、事件驱动、Agent），缺**上半截**（流程定义、并行/循环/门控、预设）。所以本轮改造里"编排"不是"闭源已有、开源不要动"，而是**开源侧要不要补、补到什么程度**的取舍问题——这需要你定。

**仍待核实（不再当既成事实写）**：九行业口径、人在环审批、反馈学习、交付与 License 计费这些是否另有闭源落点，我尚未在本机核到对应代码。

## 三、改造四块（对应商用方案的 P0/P1，标注开源可落性）

### A. 问答引擎 AI 原生化（P0，开源可落）
- 现状：规则命中为主（`ontology_qa_v3` 路径），存在"类型词作主语被抢答"这类泛化缺陷（刚修一处）。
- 目标：**本体约束优先 → 模型建议兜底 → 结论由人定**。模型只出候选答案与依据，命中依据必须可回溯到实体/关系/词典条目。
- 硬要求：① 不得引入新依赖（纯标准库 + 可选模型适配层）；② 模型输出不得绕过本体约束；③ 无法命中时如实说"未命中"，禁止编造（对标"大模型会编造情报"这条已被证实的软肋）。
- 验收：建**问答评测集**（每行业 ≥30 问，含类型词主语、多实体、否定与比较问法），改造前后跑同一套，命中率与误答率同时报。

### B. 多知识库/多行业注册表化（P0，开源可落）
- 目标：新增行业/新增知识库=注册表一行 + 数据目录，不改引擎代码（对标技能里记的"29 个 per-KB 词典碎片化"问题）。
- 硬要求：词典分层（公共工业本体层 / 工厂专属层）分开，KB 注册表统一入口，切库零重启。
- 验收：注册一个新 KB（造数据）→ 问答、图谱、词典三处都生效；删掉后无残留。

### C. 商用级加固（P1，开源可落）
- 鉴权：沿用并强化 fail-closed（缺 token 一律拒），补令牌过期与审计（留存 ≥6 个月）。
- 数据层：SQL 收口到单点，**保持 SQLite 默认**，为 MySQL 留方言适配层接口（只做接口与方言映射，不引入 MySQL 依赖）。
- 并发与性能：每请求连接生命周期、busy_timeout、慢查询与 O(n²) 热路径排查。
- 交付：Docker Compose 单机可交付、离线安装说明、升级与备份恢复步骤。
- 验收：真实浏览器 CDP 全流程（登录→问答→图谱→词典→评测）+ 断链审计（后端路由每条有前端入口）。

### D. 评测与检查工具开源化（P1，开源可落）
- 已有本体检查/数据质量核查能力，本轮补：**提问命中率评测脚本**、**断链审计脚本**、**边界检查脚本**（禁闭源 import 开源、禁甲方痕迹）。
- 验收：CI 跑绿（本地绿不算，以远端 CI 为准）。

## 四、实施纪律（血泪教训，照做）

1. **深度优先，一块做实再下一块**（历史上"一晚铺太宽"导致 bug 泛滥）。
2. **先测后交**：每块改完先回归再提交，禁止"后补测试"。
3. **按文件隔离派单**：并发改同一批文件会互相覆盖（曾 3 个任务同改一个文件）。
4. **大任务必拆小**：子代理跑大任务会预算耗尽提前收尾，每域一个独立小任务。
5. **UI 改动先确认默认态**再动手（默认显示 vs 点开显示），改前记 HEAD，跑偏立即回滚。
6. **端到端以真实浏览器为准**：curl 通 ≠ 前端已对接（曾误报"对接完成"）。
7. **每批交付物**：改动文件清单 + 自检真实输出 + 提交号；助手逐条自验后再交。

## 五、分批建议（每批一个提交，串行）

| 批次 | 内容 | 依赖 | 交付门 |
|---|---|---|---|
| 第 1 批 | 问答评测集 + 命中率基线（先量现状，不改引擎） | 无 | 基线数字落盘 |
| 第 2 批 | 问答引擎：本体约束优先 + 未命中如实说 | 第 1 批 | 命中率不降、误答率下降 |
| 第 3 批 | 模型建议层（可选适配，不引依赖） | 第 2 批 | 无模型时行为不变 |
| 第 4 批 | KB 注册表 + 词典分层 | 无 | 新增强 KB 零改代码 |
| 第 5 批 | 商用加固：鉴权/审计/连接/方言接口 | 无 | fail-closed 实测 |
| 第 6 批 | 检查工具开源化 + CI | 第 1–5 批 | 远端 CI 绿 |
| 第 7 批 | 开源净化同步（推 `D:\open-source\factory-ontology` → 远端） | 全部 | 无甲方痕迹 grep=0 |

## 六、与商用化方案的关系

商用方案第 1 步（合规定位）与第 6 步（资质）、第 4 步（License 计费）**留闭源轨道**；本规格只承担其中**开源可落的技术底座**：数据层接口、鉴权基础、多 KB 注册表、评测门。二者拼起来才是完整商用化，本轮**先把开源轨道做成可交付、可评测、可复现**。
