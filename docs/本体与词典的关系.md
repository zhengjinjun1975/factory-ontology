# 本体与词典的关系

> 结论由 `scripts/verify_ontology_lexicon_relation.py` 实测得出（valve / food / chem / auto_parts 四库，7 项断言全过）。
> 复现：`python scripts/verify_ontology_lexicon_relation.py codes/data_valve`

## 一句话

**数据 → schema → 本体** 这条主干**不经过词典**；词典是并行支线，只在两处汇入下游（工厂词典生成、问答解析），**对本体本身零影响**。

## 链路

```
CSV 数据 (data_<kb>/*.csv)
   │
   └─ suggest_schema()            ← 只吃 data / use_llm / industry
        │                            （industry 仅用于拼命名空间，不查词典）
        ├─ schema
        │    └─ build_ontology_ttl() ──► 本体
        │          类层次 rdfs:subClassOf / 对象属性 / 数据属性
        │          owl:hasKey(主键) / owl:oneOf(枚举) / owl:Restriction(基数)
        │          命名空间 {org}industry/{kb}# / versionIRI / skos:definition
        │
        └─ _build_lexicon() ──► 工厂词典 config/lexicon_<kb>.json
                                 ↑ 并入公共工业词典 industrial_dict/00_basis.json
                                   （KB 覆盖公共，公共只补 KB 没有的）

工厂词典 + 公共词典 ── load_dict() ──► 问答解析层（问句 → schema 字段/枚举值）
```

## 实测结果（四库）

手法：把 `industrial_dict_loader.merge_industrial_dict` 打桩成 no-op（**纯内存 patch，不改 industrial_dict/ 任何文件**），跑前后两遍比对产物。

| 断言 | 内容 | valve | food | chem | auto_parts |
|---|---|---|---|---|---|
| A1 | schema 推断不读词典（逐字节一致） | PASS | PASS | PASS | PASS |
| A2 | 本体 ttl 不读词典（逐字节一致） | PASS | PASS | PASS | PASS |
| A3 | 词典生成并入公共层：补入词条数 | +46 | +48 | +48 | +55 |
| A3b | 公共层只补 type/status/synonym/entity，不碰 attr/numeric 等工厂字段 | PASS | PASS | PASS | PASS |
| A4 | 问答加载再兜底一次公共层 | PASS | PASS | PASS | PASS |
| A5 | 本体中文标签 100% 可溯源到 schema | PASS | PASS | PASS | PASS |
| A5b | 词典词与本体标签是两条平行线 | PASS | PASS | PASS | PASS |

A1/A2 的关键证据：摘掉公共词典后，同一份 valve 数据推出来的 schema（sha1 `f0a0d843b0a6`）与本体 ttl（sha1 `d8a7bb07ac72`）**逐字节不变**。

A5b 的量化：valve 词典 86 个中文词，只有 43 个同时是本体标签，另 43 个只活在词典里；food 64 个里只有 23 个重合。**两份数据不共享来源，也不互为输入。**

## 本体里的中文 vs 词典里的中文

| | 来源 | 用途 |
|---|---|---|
| 本体 `rdfs:label` / `skos:definition` | schema 的 `label` / `definition`（由 data profiling + 规则生成） | 本体展示、导出给甲方 |
| 本体域类名（`设备域`→`EquipmentDomain`） | schema 的 `entity.domain` | 类层次分组 |
| 本体 `主键唯一：<pk>` | schema 的 `entity.key` | 最小公理集注释 |
| 词典 `attr_cn2en` / `type_cn2en` / `status_cn2en` / `synonym_map` | 数据 profiling + 公共词典并入 | 问答问句解析（口语 → schema 字段/枚举值） |

## 两处交汇（都是「公共词典 → 下游」）

1. `multi_model._build_lexicon`：生成工厂词典时并入 `industrial_dict/00_basis.json`，注释口径「行业认知层·建模引导」，数据推断在前、公共层补充在后。
2. `ontology_qa_v3.load_dict`：加载词典时再兜底一次，注释口径「KB 覆盖公共，公共兜底 KB」。

两处合起来说明：**公共层是行业认知的兜底层，不是本体的输入。**

## 因此确认存在的缺口

- **G1 词典不参与 schema 推断**：`suggest_schema` 签名只收 `data / use_llm / industry`，函数体不引用任何词典。词典里的①枚举值、②列名归一、③关系提示（`relations_cn2en`）、④实体识别，目前一件都没喂给建模——即「词典辅助建模」只在词典层自转，没进结构层。
- **G2 回流是手动的**：新厂词典 → 公共层需人跑 `absorb_public_dict.py --scan` 或 `POST /api/industry/absorb`；且该端点用 `threshold=1`（单厂词全吞），脚本路径才用 `CROSS_KB_THRESHOLD=3`。
- **G3 无校验门**：吸收/导入前后没有回归比对，回归脚本 `scripts/regression_qa.py`（50 条断言）未接入该流程。

## 维护约定

改动 `suggest_schema` / `_build_lexicon` / `load_dict` / `build_ontology_ttl` 任一处，都应重跑本验证：

```
python scripts/verify_ontology_lexicon_relation.py codes/data_valve
```
