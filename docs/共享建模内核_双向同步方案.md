# 共享建模内核：factory-ontology × opa-monitor 双向同步方案

> 结论先行：**以 factory-ontology 的 schema_ontology 二代引擎为共享建模内核，舆情(opa-monitor)母本体构建改为复用它，摆脱对旧 csv_to_owl + 父仓库路径的依赖**。同时提炼舆情独有的建模洞察（type_col→子类层级、对象关系语义识别、事件域叠加）作为内核增强点反哺 factory。
> 已用真实 CSV 验证关键兼容性，非纸面方案。

## 〇、资产地图（实测核对）

| | factory-ontology | opa-monitor |
|---|---|---|
| 域 | 台账问答/溯源/审计/knowledge | 舆情监控/预警/传导/风险 |
| 建模引擎 | schema_ontology.py 二代(自动推断/validate/词典/to_nt) | ontology_build→旧csv_to_owl(120行)+ontology_enhance |
| schema | ontology_schema.json + lexicon*.json | industry_schema.json(手工 type_hierarchy/object_relations) |
| 母本体 | codes/ 下各自 kb .nt | kb/mother.nt + merged.nt |
| API | ask/trace/scan/audit/knowledge | collect/alerts/trend/ask/notify |
| 事件域 | event_bus(数据变更事件) | second_modeling(舆情事件叠加) |
| 传导/风险 | 无(纯台账问答) | ontology_enhance传导 + assess风险矩阵 |

## 一、同步方向：建共享建模内核，舆情复用（用户已确认）

### 🔴 同步纪律（用户明确, 2026-09-03）
**不跨库调用; 每个库靠"拷贝"完全独立存在; 真正的代码级同步。**
- factory-ontology = 权威源(single source of truth)
- 各消费者库 = vendor/ 镜像拷贝, 库内独立运行, **不 import factory、不硬编码父仓库路径**
- 同步靠 `scripts/sync_vendor.py` 拷贝 + MD5 校验(非引用)
- 已沉淀 skill: `vendor-kernel-code-sync`

- **不硬 import**（跨库 import 违反纪律）。
- **做法**：factory 权威源文件 `csv_to_owl.py` + `data_loader.py`(均纯标准库) 经 `sync_vendor.py` **拷贝**到 opa-monitor/vendor/, 库内独立 subprocess 调用。
- 已删除 ontology_build.py 曾硬编码的 `D:/ontology-analysis/` 父仓库路径 + 跨库回退——完全自包含, 缺失即显式报错而非偷偷跨库兜底。

## 二、实测验证的兼容性结论（勿臆断）

1. **factory suggest_schema 能推断舆情 CSV**：对 mfg_products.csv 自动推断出实体 Mfg_products/主键 product_id/属性角色(category/text/reference)。✅
2. **但推断不出舆情特有语义**：①type_col(product_type=整车/动力电池) 不被识别为"子类层级"，被当普通 category 属性；②supplier/customer/region 被当 text，不被识别为"对象关系(供应商/区域)的节点值"。→ **需舆情 schema 补 type_hierarchy + object_relations**（手工声明仍必要，但可少）。
3. **factory csv_to_owl build_nt 输出缺子类层级**：只产单一主类，不产 type_col 驱动的 subClassOf。→ 舆情走的 ontology_enhance 的 type_hierarchy 增强是 factory 引擎**没有的能力**，不能简单删。
4. 舆情 kb/mother.nt 现含 20 条 suppliedBy/locatedIn 关系(enhance 补的)+类型层级，其解析器 parse_mother_nt/second_modeling 已能读——**内核输出必须兼容它读的 .nt 形态**。

## 三、共享内核设计

### 3.1 舆情建模痛点（当前）
- 依赖父仓库 `D:/ontology-analysis/src/csv_to_owl.py`(硬编码路径, 目录不在即崩)
- 两步写入：旧csv_to_owl出数据属性 + enhance补对象关系/类型层级，易漂移
- 无 validate 校验门：partOf 配了 CSV 不存在的 parent_product 列→静默0关系无警告(实测发现)

### 3.2 共享内核应提供的能力（舆情需要 且 factory已有 的）
| factory能力 | 舆情改造价值 |
|---|---|
| suggest_schema 自动推断 | 新行业(schema)时自动出雏形, 人工只补 type_hierarchy/object_relations |
| validate 校验门 | 拦 partOf 错配/type_col 列不存在 这类静默空(实测隐患) |
| 词典 lexicon | 中文/枚举/同义词统一, 舆情词收进来换行业换词典 |
| 统一 .nt 导出 | 数据+关系一步到位, 减少两套写入 |
| 自动关系推断 _infer_relations | 从 CSV 找候选对象关系, 与手写 object_relations 合并防漏 |

### 3.3 舆情反哺 factory 的点（factory 缺、舆情好的）
| 舆情能力 | factory 价值 |
|---|---|
| type_col→子类层级建模(type_hierarchy→subClassOf) | factory 只建单类, 缺"按某列拆分多个子类 + 实例归类到子类"的建模。可在 suggest_schema 里加 category列可选升级为 type_col 的提示 |
| 对象关系从数据列语义识别 | supplier/customer 这类"值指向另一个实体的数据列"应识别为对象关系候选。factory _infer_relations 可借鉴舆情的 EVENT_TYPE_COLS 定向匹配思路 |
| 事件域叠加建模(second_modeling) | factory 纯静态台账, 缺"动态事件叠加静态本体"范式(未来做监控/告警域可借鉴) |
| 传导图 + 风险参数 | factory 无传导/风险评估, 若未来扩决策域可借鉴 |

## 四、落地分步（按风险从低到高）

**阶段1 · 舆情本地化(零行为变化)**
把 schema_ontology.py + 依赖拷入 opa-monitor，ont_build 改为调本地，先不改输出。验证：重建 mother.nt 后舆情全链路(传导/问答)测试通过。

**阶段2 · 舆情加 validate 门(拦静默空)**
在 ontology_build/改 schema 校验：object_relations.node_col / type_col 引用列必须在 CSV 存在，否则报错。修复 partOf→parent_product 错配。

**阶段3 · 舆情换统一导出(去两步写)**
用内核 to_nt(支持 --relations 对象属性) 替代"旧csv_to_owl+enhance"两步，验证子类层级+对象关系仍进 .nt 且舆情解析器兼容。

**阶段4 · 反哺 factory(可选增强)**
suggest_schema 加 type_col 子类提示 + _infer_relations 借鉴舆情定向列匹配。需 factory 单测回归(75+ 不破)。

## 五、验收门（每阶段跑通才算）
- 舆情：重建 kb/*.nt → `curl /api/alerts` `/api/trend` `/api/ask` 正常 → 前端渲染正常
- 工厂：suggest_schema/validate/to_nt 单测全绿(现有 78 测试不回归)
- 兼容：舆情 parse_mother_nt/second_modeling 读内核产出 .nt 不报错

## 六、风险与边界
- 舆情演示数据(kb/*.nt 静态)重建可能改变演示效果 → 先备份原 .nt，改后可回滚
- schema_ontology 依赖 data_loader/lexicon 等 → 拷入需带全依赖，用最小集合
- 舆情模块单文件 http.server import 缓存 → 改 modules 后 kill 重启才生效
