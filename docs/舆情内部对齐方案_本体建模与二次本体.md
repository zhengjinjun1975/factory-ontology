# opa-monitor 舆情系统内部完全对齐方案（本体建模 + 二次本体）

> 目标：舆情系统内部不再维护一套与 factory 平行的建模实现，而是把**母本体建模对齐到 factory schema_ontology 二代引擎**（已拷入 vendor/），并理顺**二次本体(事件建模)**与母本体的关系。两库代码一致、建模一致、舆情独特事件域能力不丢。
> 前提已确认：schema_ontology 已同步进 opa-monitor/vendor/ 且能独立跑(实测 suggest_schema 在舆情CSV上出实体/validate 0问题/to_nt 生成)。
> 本文档先给对齐设计与分步，落地前请审。

## 〇、舆情内部建模链现状（已实测读码）

```
[母本体]  mfg_products.csv
   └→ ontology_build.build_mother      (调 vendor csv_to_owl, 出"数据属性")
   └→ ontology_enhance.enhance         (调 industry_schema, 补 is-a子类 + 对象关系)
   └→ mother.nt (含数据属性+子类+对象关系)
[二次本体] 舆情事件
   采集→sentiment负面→event_extract→second_modeling.build_event_subgraph
   └→ 事件作为新实例(hasTarget关联到母本体节点) → merged.nt
[读侧] parse_mother_nt / parse_events / _load_triples (自写正则解析 .nt)
```

**痛点**：
1. 母本体**两步写入**(csv_to_owl 出数据属性 + enhance 补子类/关系)，两套逻辑易漂移
2. 舆情自写 .nt 解析器(parse_mother_nt 等)与 factory schema_ontology 的建模是**两套平行实现**，不共享
3. schema_ontology 已拷入 vendor 但**舆情建模链完全没调它**——代码一致了，行为没对齐
4. 二次本体(事件)子图写入 merged.nt 用自写三元组拼接，与 factory 无对应范式

## 一、对齐目标

把舆情母本体建模从"csv_to_owl+enhance 两步手写"改为"schema_ontology 二代引擎一步建模"，二次本体事件建模**数据形态对齐**(统一 .nt 读取/写入)，舆情独特的事件域(事件叠加母本体/风险传导/预警)保留在舆情侧实现。

### 对齐后的内部链(目标)
```
[母本体]  mfg_products.csv
   └→ schema_ontology: suggest_schema → (补schema) → validate → to_nt
   └→ mother.nt (一步含 数据属性+子类层级+对象关系)
[二次本体] 舆情事件
   事件抽取 → 事件实例(hasTarget→母本体节点) → merged.nt
[读侧] 统一用 schema_ontology 产出的 .nt + 舆情事件解析
```

## 二、需解决的关键差异(schema_ontology vs 舆情现状) — 勿臆断, 已实测

1. **子类层级列名**：schema_ontology 的 is-a 子类建模**只认字面 "category" 列**(L617 `"category" not in data[table][0]`)，但舆情 CSV 用 `product_type`(值=整车/动力电池)。suggest_schema 已把 product_type 识别为 role=category，但 to_nt 的 hasCategory/isA 不认非 "category" 名 → 需增强让"role=category 的任意列"都建子类。
2. **对象关系来源**：舆情 enhance 从 industry_schema.object_relations 手工声明建 suppliedBy/locatedIn；schema_ontology 靠 _infer_relations 从 CSV 自动推断(可能把 supplier 当 text)。舆情的关系语义(suppliedBy=供应商)是领域知识，schema_ontology 规则推断可能推断不出 → 需 schema 显式声明对象关系的能力(schema_ontology 是否支持 schema 里手工声明 relations?待查)。
3. **事件二次本体**：factory schema_ontology 无"事件"概念(纯静态台账)。舆情事件建模是**舆情侧实现**(保留在 second_modeling)，但 .nt 读写可与 schema_ontology 统一风格。

## 三、对齐分步(每步可验收)

### 阶段 A · 舆情母本体切到 schema_ontology(核心)
- 改 server.py `/api/build`(L297-303) + main.py：从"build_mother+enhance"改为调 vendor schema_ontology(suggest_schema→validate→to_nt)。
- **难点**：解决上述差异1(子类列名通用化)与差异2(对象关系)。
- 若差异1需改 schema_ontology 源码 → 会牵动 factory 本体建模，须在 factory 侧改(single source)再 sync_vendor, 且 factory 现有测试(78)回归。

### 阶段 B · 二次本体事件建模对齐
- 事件子图写入保留(舆情独有), 但事件三元组风格与 schema_ontology 一致(用统一 NS/类型声明)。
- 读侧解析事件可与 factory 数据形态对齐。

### 阶段 C · 统一读侧
- 舆情 parse_mother_nt 与 factory 建模产出的 .nt 兼容性验证(舆情解析器读 schema_ontology 产出的 mother.nt)。

## 四、风险与红线
- **动 schema_ontology 源码会双向影响**(factory+舆情都要回归)。优先找"不改权威源"的对齐路径(如舆情 schema 显式声明、或舆情侧包装)。
- 舆情演示数据(kb/*.nt 静态)重建可能改变前端展示 → 备份可回滚。
- server.py 单文件 http.server 改模块需 kill 重启才生效(skill 已知坑)。

## 五、待确认(落地前)
1. schema_ontology 是否支持 schema 内**手工声明对象关系**(suppliedBy)而非只靠规则推断? 查 build_ontology_model 的 relations 处理。
2. 差异1(子类列名)能否在舆情侧不改 schema_ontology 源码解决(如 to_nt 前把 product_type 列改名为 category? 不优雅)——还是必须改权威源?
3. 用户希望舆情"完全用 factory 引擎"到什么程度——是否接受动 schema_ontology 源码增强(需 factory 回归)?
