## 1.2 数据流（问答主链）

```
提问 → api_server（鉴权 fail-closed）
     → ask_service 选路
     → 规则命中原语（ontology_qa_v3）──命中──▶ 证据回填（evidence）→ 答案 + 依据
                                     └─未命中─▶ 逻辑/检索（logical_qa / BM25 / 向量 / 图谱 RAG / SPARQL）
                                              → fusion 融合 → 证据回填 → 答案或“未命中”
     → 全过程落 audit_chain
     → 前端经 web/ BFF 展示（版本号、依据、图谱）
```

## 1.3 边界（本轮收敛，纠正前版臆断）

- **本库承载**：算法与引擎（建模、问答、检索、图谱、词典、质量与评测）+ 装配骨架（插件框架、事件总线、Agent）+ 可开源的商用基础（鉴权基础、离线部署、评测门）。
- **不进本库**：License 授权与计费、资质材料（软著/检测报告/等保密评）、甲方数据与甲方痕迹。
- **待你定** → **已定：要补**。编排的"上半截"（流程定义、并行/分支/循环/门控、预设卡）**补进本库**，与现有下半截（原子装配 + 能力路由 + 事件驱动）拼成套。设计见 §1.5。
- **九行业（已查实）**：落在 `codes/config/kbs.json`，共 **33 个知识库**；前 22 个是行业口径（能源站、通用制造、五金加工、食品溯源、阀门、化工、波纹管、地震勘探、环保、机械、船舶、智能设备预测性维护、图书、汽车零部件、电子元件、家电、纺织、塑料、医疗器械、家具、阳光电力等），其余 11 个是测试/onboarding/重复项（`valve2/valve3/valve9`、`e2ecust`、`factory_multi_*`、`onb_*`）。**以本地与远端代码为准**，不再引用技能里的旧描述。
- **⚠️ 开源卫生项（用户已裁决）**：`kbs.json` 里有 `huaneng`（华能）。用户 2026-09-24 明确：**本地无所谓，远端再做脱敏**；且它**本质不是实际公司**（非真实甲方名）→ 降为**发布前例行改名**，不作为红线风险，随批 7 开源净化一起处理。

## 1.4 编排上半截设计（本轮新增，用户已定"要"）

**目标**：让本库能定义并运行一条**带控制流的流程**，而不仅是"一次调用"。

**设计要点（贴合现有装配层，不另起炉灶）**
- **流程定义**：新增 `codes/flows/` 目录，一份 JSON 一份流程（`{flow_id, name, steps[], edges[], preset?}`），与 `plugin_framework` 的 manifest 风格保持一致。
- **原子来源**：步骤引用**已有能力**（问答/检索/图谱/检查/评测）或插件扩展点 `(kind, id)`，经 `reg.call(kind, id, params)` 执行——**不新增执行体系**。
- **控制流**：`parallel`（同列并行）、`branch`（条件分支）、`loop`（带出口条件的循环）、`gate`（门控：按上游证据判定放行/打回）。循环与门控必须在流程定义里可读（谁能一眼看出回到上游哪一步）。
- **预设卡**：`preset: true` 的流程在前端口列出（如"全量本体体检""问答质量回归""词典缺失补全"），点一下即跑。
- **事件与审计**：每一步结果写 `event_bus`，全过程落 `audit_chain`，支持按时间线回放。
- **失败处理**：任一步失败**如实写原因并停在该步**，禁止静默吞；上游无输入时如实写"没有输入"，不判整条失败。
- **开源边界**：只做**通用流程引擎**，不含行业口径与甲方业务规则；行业相关的预设卡放配置而非代码。

**验收门**：① 一条 5 步流程（含并行 + 门控）能跑通并有事件流；② 门控打回后能回到指定上游步；③ 流程加载失败必须在界面/接口写出真实原因，界面不装作没事；④ 预设卡与流程定义一一对应，不另写说明书。



## 1.5 部署形态

现有：`Dockerfile`、`docker-compose.yml`、`nginx.conf`、`start.sh/.bat`。
目标：单机 Compose 可交付 + 离线安装 + 带校验升级 + 备份恢复演练（对应商用方案第 5 步）。
数据层：**保持 SQLite 默认**，抽出方言适配接口，MySQL/国产库作为可选后端接入（不引入依赖）。

# 第二部分 需求分析

## 2.1 干系人

| 角色 | 关心什么 |
|---|---|
| 甲方工程师 | 问得准、有依据、不编造；本地跑、数据不出厂 |
| 知识管理员 | 词典与本体可维护、新增行业不改代码 |
| 交付实施 | 一小时内能装起来、升级不丢数据 |
| 第三方开发者 | 不改主程序就能加能力（插件） |
| 我方产品 | 可评测、可复现、可对外讲效果 |

## 2.2 功能性需求（FR）

| 编号 | 需求 | 现状 | 判定标准 |
|---|---|---|---|
| FR-1 | 问答必须给**可回溯依据**（实体/关系/词典条目） | 部分具备（evidence.py） | 每条答案带依据字段，缺依据视为不通过 |
| FR-2 | **未命中要如实说"未命中"**，禁止编造 | 待核 | 评测集里"无答案类"问题零编造 |
| FR-3 | 模型只出候选与建议，**结论由人定** | 待建 | 引入模型后，无模型时行为不变（可回归证明） |
| FR-4 | 新增行业/知识库**不改引擎代码** | 部分具备（词典与 KB 分散） | 注册一行 + 数据目录即生效 |
| FR-5 | 词典分层（公共工业本体层 / 工厂专属层）可分别维护 | 部分具备 | 两层可独立增删，互不覆盖 |
| FR-6 | 问答命中率**可量化** | 缺基线 | 每行业 ≥30 问的评测集 + 命中率/误答率基线落盘 |
| FR-7 | 插件可不改主程序扩展能力 | 已具备 | 插件目录放入即被扫描，缺字段容错不中断 |
| FR-8 | 审计可追溯（谁在何时问了什么、系统答了什么） | 部分具备（audit_chain） | 可按时间线回放 |
| FR-9 | 鉴权 fail-closed | 已具备（待复核覆盖面） | 缺 token 一律拒；错 token 拒 |
| FR-10 | 断开链检查（后端每条路由有前端入口） | 缺 | 脚本化，纳入 CI |

## 2.3 非功能性需求（NFR）

| 编号 | 需求 | 指标 |
|---|---|---|
| NFR-1 | 零第三方依赖（核心） | 核心路径纯标准库；可选能力放 `requirements-optional.txt` |
| NFR-2 | 离线可运行 | 无外网可启动、可问答 |
| NFR-3 | 数据不出厂 | 无外部服务调用；本地模型可选 |
| NFR-4 | 部署时长 | 单机 Compose 一小时内可起 |
| NFR-5 | 升级与回滚 | 带校验的迁移脚本；回滚保留旧库只读 |
| NFR-6 | 并发 | 每请求连接生命周期 + busy_timeout；压测给 p95 |
| NFR-7 | 审计留存 | ≥6 个月可导出 |
| NFR-8 | 可开源合规 | 库内零甲方痕迹；许可证与 NOTICE 齐 |

## 2.4 约束与风险

- **约束**：纯标准库纪律；不改动甲方数据；开源库内不得出现客户名。
- **风险 R1**：模型接入引发"看起来更聪明、实际更不可靠"——用"未命中如实说"与评测集卡住。
- **风险 R2**：广度铺太宽导致 bug 泛滥（历史教训）——分批串行、先测后交。
- **风险 R3**：并发改同一批文件互相覆盖——按文件隔离派单。

# 第三部分 需求设计

## 3.1 模块设计（改动落点）

| 目标 | 落点模块 | 设计要点 |
|---|---|---|
| 问答可追溯与未命中 | `ontology_qa_v3.py`、`ask_service.py`、`evidence.py` | 统一返回信封：`{answer, evidence[], hit: bool, reason}`；`hit=false` 时 `answer` 明示未命中 |
| 模型建议层 | 新增 `model_advisory.py`（可选） | 适配器模式，未配置模型则**不启用**；输出必须带 `candidates[]` 与 `basis[]` |
| 评测基线 | 新增 `scripts/eval_qa.py` + `codes/tests/fixtures/qa_eval/*.json` | 每行业 ≥30 问；输出命中率、误答率、未命中率三数 |
| KB 注册表 | `ontology_schema_info.py` 或新增 `kb_registry.py` | 注册表统一入口：`{kb_id, 行业, 数据目录, 词典层}`；切库零重启 |
| 词典分层 | `industrial_dict_loader.py`、`absorb_public_dict.py`、`dict_asset.py` | 公共层只读、专属层可写；冲突时报错不静默覆盖 |
| 方言适配 | 新增 `db_dialect.py`（薄层） | SQL 收口单点；SQLite 默认；MySQL 仅留映射与接口 |
| 审计与鉴权 | `api_server.py`、`audit_chain.py` | 令牌过期与刷新；审计含主体/时间/问题/答案/依据 |
| 断链与边界检查 | `scripts/`（复用 `ontology_check` 风格） | 路由↔前端入口、禁闭源 import、禁甲方痕迹 |

## 3.2 接口契约（问答主接口）

```
POST /api/ask        {kb, question, options?}
200 → {answer: str, hit: bool, reason: str,
       evidence: [{kind:"entity|relation|dict|doc", id, label, source}],
       advisory?: {candidates: [...], basis: [...], model: "..."} }
4xx → 参数错误（含 kb 不存在）；5xx → 不吞异常，返回可读原因
```
纪律：**不新增依赖**；错误不静默吞；缺依赖/未实现 → 501（沿用现有约定）。

## 3.3 关键流程（未命中处理）

```
提问 → 规则命中? ──是──▶ 证据回填 → 返回答案(hit=true)
               └─否─▶ 逻辑/检索 ──命中──▶ 融合 → 证据回填 → hit=true
                                └─否─▶ advisory 有配置? ──是──▶ 返回候选(仍 hit=false，标注“建议候选，需人工确认”)
                                                      └─否─▶ 返回 hit=false + reason="未命中，无可靠依据"
```
硬红线：**任何分支都不得把模型生成内容当成结论返回**。

# 第四部分 实施准备

## 4.1 批次与门（串行，每批一个提交）

| 批次 | 交付 | 关键门 | 依赖 |
|---|---|---|---|
| 1 | 评测集 + 命中率基线（不动引擎） | 基线三数落盘 | — |
| 2 | 问答统一信封 + 未命中如实说 | 命中率不降、误答率下降 | 1 |
| 3 | 模型建议层（可选适配） | 无模型时行为与批 2 完全一致 | 2 |
| 4 | KB 注册表 + 词典分层 | 新增 KB 零改代码 | — |
| 4b | **编排上半截**：流程定义 + 并行/分支/循环/门控 + 预设卡（§1.4） | 5 步流程跑通、门控可打回、加载失败如实报因 | 4 |
| 5 | 商用加固（鉴权/审计/连接/方言接口） | fail-closed 实测 + 压测 p95 | — |
| 6 | 检查工具开源化 + CI | 远端 CI 绿 | 1–5 |
| 7 | 开源净化同步 + 推远端 | 甲方痕迹 grep=0 | 全部 |

## 4.2 派单纪律

按文件隔离派单；大任务拆小（每域一个独立任务）；每批交付物必须含**改动文件清单 + 自检真实输出 + 提交号**；UI 改动先确认默认态；端到端以真实浏览器为准。

## 4.3 验收总纲

1. 每批自检脚本从终端跑，输出真实结果（不接受"代码存在"）。
2. 问答类改动必须跑同一套评测集，**跨批数字可比**。
3. 端到端：真实浏览器走 登录→问答→图谱→词典→评测 全流程。
4. 每批提交后跑断链审计与边界检查。
