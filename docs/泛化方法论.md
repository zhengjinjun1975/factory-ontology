# 领域无关的泛化方法论：本体建模到自然语言问答

大模型写得出诗，数不清表里有多少行。不是它笨，是它没见过你的表。把裸表直接丢给模型，模型只能靠猜，猜出来的数字还格外自信。这个问题不解决，再强的模型落到工厂数据上都是空中楼阁。本文档记录这个仓库的解法：在数据和模型之间建一座结构化的桥。桥的一端是确定的，另一端才轮到模型发挥。配套实证见 [方法论文-本体vs裸LLM](方法论文-本体vs裸LLM.md)。

## 一、核心思想

**大模型落地难，难在领域知识和数据之间没有桥。** 本体建模就是这座桥：把裸表变成"实体-关系-属性"的语义结构，让规则引擎和大模型都能读懂数据。

```
原始数据 → 本体建模（schema 驱动）→ 本体驱动混合检索（规则 + 图 + BM25）+ 本体约束减幻觉 → 自然语言问答
```

三个原则贯穿始终：

1. **确定性优先**：规则能答的，不让 LLM 答。结构化查询是精确计算，规则引擎按定义算，结果可复现、零 token、零幻觉
2. **LLM 只做泛化**：规则覆盖不到的模糊问题才走 LLM，且用本体约束圈住它的回答范围
3. **本体要轻**：这里说的本体是一份受限 schema，不是 W3C 的完整 OWL 推理体系。够用、快、能落地，比完备更重要

## 二、schema 驱动建模

建模层只有一个入口：`schema_ontology.py`。它把多张表 + 一份 schema 统一成一张"实体-关系-属性"图，输出标准 N-Triples。下游的规则引擎和 GraphRAG 消费同一份产物。

schema 是一份 JSON，声明四类信息：

| 声明 | 内容 | 作用 |
|------|------|------|
| 实体 | 有哪些类、对应哪些表 | 决定实例怎么建 |
| 关系 | 表与表之间的关联 | 跨表查询、溯源链 |
| 属性角色 | identifier / reference / measure / category / timestamp | 字段语义归类，驱动模板匹配 |
| 约束 | 必填、类型、引用完整性 | validate 校验，建模失败给出明确原因 |

配套能力：

- **类型体系**：Enterprise → BusinessObject → 域类 → 实体。类别层级自动生成，产品 Is-A 类别，实例挂 hasType 链接
- **validate**：约束校验。实体 id 重复、关系引用不存在、schema JSON 非法，逐项报告，不裸抛异常
- **traverse**：跨域图遍历。从任一实体出发，沿关系拿到关联实体，溯源和子图检索都靠它
- **build_graph**：跨表统一实例图。外键自动识别成对象属性，多表 join 语义显式化
- **suggest_schema**：没有手写 schema 时，从数据自动推断实体、关系和约束。实测可从 8 张表推断出 8 实体 8 关系
- **to_nt**：N-Triples 统一输出。类名表名风格（Valve_products）+ 对象属性英文 id（usesRawMaterial），下游无缝消费

建模失败的每步都有报告：数据目录不存在、schema 非法、id 重复、关系悬空，原因直接打出来，便于现场排障。

## 三、本体驱动混合检索

问答链路按确定性从高到低排列：

```
规则引擎（ontology_qa_v3）→ 逻辑桥（logical_qa）→ 本体引导 GraphRAG → BM25 → miss
```

**规则引擎**是主力。通用模板覆盖结构化查询：数量、极值、TopN、平均、总和、范围、过滤计数、反查、分组、列出。模板不硬编码任何中文词，属性名和枚举值全部从词典读。

**本体引导 GraphRAG** 处理开放式和关系问题。种子定位时，如果问题匹配本体里的关系 label，沿关系路径扩展种子（`find_seeds(ontology=...)`），多跳查询的召回明显好于纯文本匹配。这个方向的依据来自外部研究：本体关系路径引导知识图谱检索，能显著提升多跳问答（OG-RAG，EMNLP 2025；ORT，ACL 2025）；OntoRAG 在复杂多跳查询上优于纯向量 RAG（报告 85%/75%）。这些是外部结论，用来校准方向；本仓库自己的数字见第六节。

**检索容错**解决工业数据的真实脏乱。材质、单位、类型做同义词扩展：问"不锈钢"，命中 CF8/CF8M/304/1Cr18Ni9Ti 全部牌号；缺失值和异常值检索不崩。

## 四、本体约束减幻觉

LLM 兜底时，prompt 注入本体约束：只依据子图里的事实回答，不编造图中不存在的关系和实体。这个做法的依据来自临床问答研究（本体约束下 98% vs 裸 GPT-4 37%，幻觉率降幅超过 61%）。本仓库的实现是三个动作：本体引导种子定位、子图抽取、约束 prompt。模型能看到的只有本体圈定的范围，编造的空间被压缩到最小。

## 五、词典驱动：换领域只换配置

领域无关的关键在分层。数据→本体、问答逻辑这两层不绑定任何具体工厂；唯一绑定领域的词典层，由 LLM 自动推断生成。

| 层 | 是否依赖具体领域 | 做法 |
|----|----------------|------|
| 数据→本体 | 否 | 任意 CSV 自动转本体（schema 驱动 + suggest_schema 推断） |
| 词典/字段 | 是 | LLM 推断字段语义自动生成，换领域换词典 |
| 问答逻辑 | 否 | 通用模板（数量/极值/范围/统计/组合/过滤计数） |

换工厂时，代码一行不动。实测：同一个规则引擎，在制造业、图书、能源、食品、阀门五个领域全部 100% 命中（第六节）。

## 六、实证：五领域 benchmark

方法：标准答案从源数据用确定性逻辑计算（数量/极值/平均/总和/过滤计数），不手写答案。同一批问题跑本体规则引擎（零模型、确定性），算命中率。

| 领域 | 数据集 | 规模 | 评测问题 | 本体命中率 |
|------|--------|------|----------|-----------|
| 制造业（预测性维护） | UCI AI4I（公开） | 10,000 行 / 14 列 | 61 | **61/61 = 100%** |
| 图书库存 | library_inventory（合成） | 10 行 | 13 | **13/13 = 100%** |
| 能源电站设备 | energy_station（合成） | 10 行 | 13 | **13/13 = 100%** |
| 食品企业 | food_products（合成） | 8 产品 | 9 | **9/9 = 100%** |
| 阀门厂 | valve_products（合成） | 8 表 → 1066 行 NT | 9 | **9/9 = 100%** |

对照实验（食品领域，方法论文记录）：裸 LLM 不加本体、直接把数据喂给模型，同批问题 7/9 = 78%。差的恰好是计算类：平均值、总和。这是大模型最典型的计算幻觉，也是规则引擎最稳的强项。

其他实证：GraphRAG 开放式问题 8/8；同义词容错 8/8（"不锈钢"命中 CF8 系列）；20 万实体 SQLite 图持久化写入 1.58s、加载 1.76s、67MB。

复现（全部可跑，无需 LLM 和 API key）：

```bash
cd codes
python csv_to_owl.py data/ai4i.csv output/ai4i.nt
python benchmark.py data/ai4i.csv               # 61/61
python csv_to_owl.py data/library_inventory.csv output/library_inventory.nt
python benchmark.py data/library_inventory.csv  # 13/13
python csv_to_owl.py data/energy_station.csv output/energy_station.nt
python benchmark.py data/energy_station.csv     # 13/13
python benchmark.py data/food_products.csv      # 9/9
python valve_demo.py                            # 阀门示例 + benchmark 9/9
python -m pytest tests                          # 29 项单测
```

## 七、边界

- **数据形态**：最适配结构化台账（单表/多表 CSV）。时序数据、非结构化文本不在当前能力内
- **模板范围**：规则引擎覆盖结构化查询模板；开放式/关系/模糊问题走 GraphRAG 或 LLM，命中率不保证
- **本体定位**：受限 schema，非 W3C OWL 推理本体，不涉及推理机
- **词典校对**：自动词典偶有误判，关键字段需人工确认
- **规模**：内存图为主，台账级；百万级实体图不在设计目标内
- **LLM 稳定性**：本地小模型偶发空响应，生产建议用更强模型

## 八、决策准则

- 先问"数据在哪、要解决什么问题"，再谈技术选型
- 能自动就别手写：schema 推断、词典生成、类型推断全自动化，人工只校对关键字段
- 规则能答的别让 LLM 答：省 token、快、准、可复现
- 本体约束永远在场：模型可以答错，不可以编造

泛化的尽头不是更强的模型，而是更少的假设。这个仓库把假设全部外置成 schema 和词典，模型只负责在圈子里说话。圈子画得越准，答案越可信。
