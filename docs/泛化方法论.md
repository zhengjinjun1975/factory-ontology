# 领域无关泛化方法论：本体建模 → 大模型落地

> 本仓库的核心方法论，换任何工厂或领域只换数据、代码不动。本文是设计原则 + 实证，含可复现 benchmark。

## 为什么做本体建模

大模型落地难，难在“领域知识”和“数据”之间没有桥。裸表是一个个平面文件，字段名是机器语言，大模型读得懂字面，读不懂业务含义。本体建模就是这座桥：把裸表变成“实体-关系-属性”的语义结构，让规则引擎和大模型都能真正理解数据在说什么。

```
原始数据 → 本体建模(schema驱动) → 原子智能体 → 编排 → 大模型应用
                    ↓
        本体驱动混合检索(规则+图+BM25) + 本体约束减幻觉
```

一句话说清定位：**不是用模型直接查数据，而是先把数据变成模型能理解的业务结构，再在这个结构上回答。** 这个先后顺序，决定了答案能不能溯源、能不能复现、要不要烧 token。

## 2026 本体驱动增强

这一节总结了这轮升级的核心，每一条都对应 2025-2026 的研究依据（详见 `knowledge/AI/articles/` 三篇研究笔记），不是拍脑袋：

| 增强 | 依据 | 落地 |
|------|------|------|
| **schema 驱动建模**（`schema_ontology.py` + `suggest_schema` 自动推断） | LLM/规则驱动本体自动构建（LOM、schema-free 范式） | 有手写 schema 或 `suggest_schema` 自动推断，都能建统一本体 |
| **本体引导 GraphRAG 种子**（`find_seeds(ontology=...)`） | 本体关系路径引导 KG 检索显著提升多跳问答（OG-RAG EMNLP2025、ORT ACL2025） | 问题匹配关系 label 时，沿关系扩展种子 |
| **本体约束减幻觉**（LLM prompt 注入本体约束） | 本体约束减幻觉（临床 QA 98% vs GPT-4 37%，幻觉率降 >61%） | 只依据子图事实回答，不编造图中不存在的关系/实体 |

三条增强指向同一个判断：纯向量 RAG 在复杂多跳查询上有天花板，本体引导的检索能显著改善。但本仓库的用法是“规则确定 + 本体增强”，LLM 只做兜底，把模型幻觉的风险压到最小。

## 核心：词典驱动，代码不绑数据

问答逻辑不绑定具体词表，靠词典驱动。换数据源只换词典，代码不动。

| 层 | 是否依赖具体工厂 | 做法 |
|----|----------------|------|
| 数据→本体 | 否 | 任何 CSV 自动转本体（类型自动推断） |
| 词典/字段 | 是 | 全自动生成(LLM推断)，换工厂换词典 |
| 问答逻辑 | 否 | 通用模板(数量/极值/范围/统计/组合/过滤计数) |

这条是“领域无关”的根基。三张表的分工很干净：数据到本体是普适的，词典是领域相关的但全自动，问答逻辑完全通用。换一个工厂，动的只有词典这一层。

## 五条可迁移设计原则

1. **建模是桥不是终点**： 让大模型“懂领域”，别为建模而建模
2. **原子智能体是积木**： 单一职责、可组合、可替换
3. **编排器是组织者**： 轻量调度器按任务类型路由，零依赖可部署现场
4. **泛化靠外置**： 词典/字段映射外置成配置，换领域只换配置
5. **规则兜底 + LLM 泛化**： 确定性走规则(快准零成本)，模糊走 LLM(灵活)

## 规则引擎的模板集（确定性部分）

规则引擎用通用模板回答结构化问题，不硬编码任何具体中文词，属性名和枚举值全部从词典读：
- 数量：多少台/个/条
- 组合：状态词的类型词（报警的焊接机器人）
- 区域：区域/车间的设备
- 列出：列出所有X
- 极值：属性最大/最小
- TopN：属性最高的N个
- 平均 / 总和
- 范围：大于/小于/在A到B之间
- 分组：按X统计
- **过滤计数：属性=N 的数量**（如“机器故障标签=1 的数量”）
- 反查：哪些属性=值

这些模板覆盖了工厂台账查询的主流需求。模板的好处是可复现、零 token、结果精确，这也是“规则优先”能立住的底气。

## 实证：本体问答 benchmark（可复现）

`benchmark.py` 验证“本体建模提升检索命中率”：从源数据用确定性逻辑算标准答案，同一批问题跑本体规则引擎（零模型），算命中率。

**结果：3 个不同领域数据集全部 100% 命中。**

| 领域 | 数据集 | 行数 | 评测问题 | 本体命中率 |
|------|--------|------|----------|-----------|
| 制造业（预测性维护） | UCI AI4I | 10000 | 61 | **61/61 = 100%** |
| 图书库存 | library_inventory（示例） | 10 | 13 | **13/13 = 100%** |
| 能源电站设备 | energy_station（示例） | 10 | 13 | **13/13 = 100%** |

这个结果证明“领域无关泛化”立得住：换任何领域的 CSV，自动建本体加词典后，规则引擎结构化查询确定性 100% 命中。

```bash
python benchmark.py data/ai4i.csv               # 制造业
python benchmark.py data/library_inventory.csv  # 图书库存
python benchmark.py data/energy_station.csv     # 能源电站
python benchmark.py data/ai4i.csv --llm          # 加纯 LLM 对照
```

**关键判断**：这 100% 是“本体 vs 裸数据/裸 LLM”的核心优势，可复现、零 token、结果精确。但要说清边界，它只覆盖结构化查询。开放式、关系性、模糊问题，规则引擎覆盖不到，交给 GraphRAG 或 LLM 兜底，命中率不做承诺。

## 换工厂/换领域 3 步（现场落地）

1. **转本体**：`python csv_to_owl.py 你的数据.csv output.nt`
2. **自动词典**：`run.py setup` 自动生成（或手写精简词典）
3. **直接问**：通用模板引擎 `ontology_qa_v3` 回答

## 诚实边界

- 数据形态：最适配“结构化台账/单表”，时序、多表需扩展
- 语义校对：自动词典偶有误判，需人确认关键字段
- LLM 稳定性：本地模型偶发空响应，生产用更强模型
- 数据源：核心支持 CSV；Excel/DB 需导出或走 data_loader
- 规则模板覆盖结构化查询；开放式/模糊问题才走 LLM 兜底

不藏着这些边界，是因为“确定性”这个卖点建立在“只对结构化查询承诺”之上。把边界说清楚，比把 100% 说成万能更值钱。

## 决策准则

- 先问“数据在哪、要解决什么问题”，再谈技术
- 能自动就别手写：词典/类型推断/本体补全都自动化
- 规则能答的别让 LLM 答：省 token、快、准、可复现
