## 二、自动匹配规则表（从真实数据枚举，不写死）

**候选来源（两条，合并去重）**
1. `codes/config/kbs.json` 里所有已注册 kb 的 `data_dir`（相对 `codes/`）；
2. `codes/` 下所有**真实存在**的 `data*` 目录（`data` / `data_valve` / `data_food` …，只取目录，排除 `data_loader.py` 等文件）。

**kb ↔ 数据目录 双向推导**

| 方向 | 规则 | 例 |
|---|---|---|
| 输入 kb 名 → 目录 | 规范化（小写）匹配：① 该 kb 已注册的 `data_dir`；② `data_<kb>` 目录；输入即自动高亮/选中 | 输入 `valve` → 选中 `data_valve` |
| 选中目录 → 建议 kb | `data_xxx` → `xxx`；纯 `data` 无后缀 → 无法唯一推导（留空） | 选中 `data_precision` → 建议 kb `precision` |

**每个候选项显示的证据**：目录是否存在 / CSV 个数 / 已被哪些 kb 注册 / 建议 kb / 是否外部数据目录 / 是否与当前 kb 冲突。

**默认态（打开面板即列真实候选）**
1. 当前 kb 有已注册候选 → 默认选中它；
2. 否则全库**唯一已注册 KB** → 选中它的目录；
3. 否则**留空**并提示「请从候选中选择」（**绝不回退到写死值**）。

**选中后校验（blocked 即挡住「AI 建议」）**：危险路径（盘符根 / 系统目录）→ 拦；不存在 / 不是目录 / 不可读 / 无 CSV → 拦；已被**别的** kb 占用（冲突）→ 拦。**未匹配到任何已注册目录**时不静默回退，显式提示「未匹配到已注册目录，这是一个新目录，请确认后继续」并要求勾选「确认使用新目录」。

**外部数据目录**：支持仓库外绝对路径；界面标「外部数据目录」，并写入 `kbs.json` 的 `entry.external=true`（交付清单可据此列出）。

**危险路径拦截（BFF 与后端同口径）**：盘符根（`C:/`）、文件系统根（`/`）、系统目录（`C:/Windows`、`C:/Program Files`、`C:/ProgramData`、`/etc`、`/usr`、`/bin`、`/sys` …）。

## 四、反向断链 `/api/ontology/self-onboard` 的结论与选择理由

**查清**：`web/src/**` 与页面层**没有任何**对 `/api/ontology/self-onboard` 的引用 —— 不存在「前端调错路径」；
真实情况是 `web/server/ontology.js` 里有一段 **`selfOnboard()` 死转发函数**（向一个后端从未实现的端点转发），
且**没有任何 BFF 路由引用它**。即：**后端缺路由 + BFF 侧未接线**，检查工具把它报为「反向断链」。

**选择：补后端路由（而非删死代码）**，理由：
1. 该函数的语义是真实能力（甲方自助接入：上传数据文件 → 落盘 `data_<kb>/` → 自动建模+词典 → 返回可用 kb），
   删掉等于放弃能力，且与「自助建模」本次主题一致；
2. 补齐后链路闭合：后端路由存在 ← `ontology.js` 转发 ← BFF 路由 ← 前端封装（`api.js`），
   `check_chainbreak.py` 该条由 `[XX]` 变 `[OK] POST /api/ontology/self-onboard 经BFF(SPA)`，**反向断链 0**。

**证据**：`check_chainbreak.py` 输出——
```
[OK] POST /api/ontology/self-onboard             经BFF(SPA)
        证据(SPA) : BFF /api/ontology/self-onboard <- web\src\lib\api.js
[OK] /api/ontology/self-onboard
[反向汇总] BFF 指向不存在端点: 0
```
（正向断链仍为 26 项，均为**改动前既有**、非本次引入，且不在 8 道门内；本次未扩大。）
