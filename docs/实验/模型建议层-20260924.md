## 三、设计要点（对照规格逐条）

1. **适配器模式 / 默认不启用（规格 ①）**
   `is_enabled()` 的四道判据，任一不满足即 False：
   - 必须**显式**打开：`FACTORY_ADVISORY_ENABLE=1` 或 `FACTORY_ADVISORY_MODEL=<模型名>`
     或存在 `codes/config/model_advisory.json` 且 `enabled=true`；
     三者默认都不存在 → **默认关闭**。
     （刻意**不**用 `model_llm` 那套 `ZHIPU_API_KEY`/`DEEPSEEK_API_KEY`——本机环境变量里确实有
     `ZHIPU_API_KEY`，若按"有 key 就启用"会把默认态误开。建议层的开关必须是自己的一套 env。）
   - 必须解析到适配器：显式注入的 > 已注册的 > 由配置构造的内置 Ollama 适配器。
   - 适配器 `requires_key=True` 时必须有 `FACTORY_ADVISORY_API_KEY`。
   - 适配器 `available()` 为真。
2. **产物只能进 advisory，hit 按批 2 判定（规格 ②）**
   - 产物恒为 `{"candidates": [...], "basis": [...], "model": "..."}`，**恰好三键**，
     由 `build_advisory()` 收口（去重/去空）；候选与依据都为空 → 返回 `None`（不产空壳）。
   - `attach_if_enabled()` 只允许新增 `advisory` 一个键；`hit` 由批 2 的 `envelope_from_result`
     原逻辑算出，建议层从不读也不写它。
3. **红线有断言（规格 ③）**
   - 自检脚本对 331 题逐条断言"候选/依据文本不出现在 answer 中"。
   - 更进一层：模块内置**运行期闸门** `_leaks_into_answer()`——一旦发现 advisory 文本出现在
     `answer` 里，或 answer/hit 与入参不一致，就**丢弃 advisory** 并写 `advisory_error`（保守失败）。
     负样本测试证明这道闸真的会红（见 §五.3）。
4. **界面文案（规格 ④，本批未改前端）** —— 建议文案见 §六。
5. **自检（规格 ⑤）** —— `scripts/verify_advisory.py`，见 §五。
6. **报告（规格 ⑥）** —— 本文件，含「没做到/不确定项」。

## 六、界面文案建议（规格 ④，本批未改前端）

本批不改 `web/`。若后续要展示 `advisory`，**必须**按下列文案与位置约束（防止用户把它当结论）：

1. 区块标题固定为：**「建议候选，需人工确认」**（可直接用这个字符串做 UI 断言）。

5. 前端读取建议：`if (resp.advisory && resp.advisory.candidates?.length)` 才渲染区块；

前端最小提交物（**待后续批次实施，本批未做**）：`web/` 问答结果卡片里加一个独立 `advisory` 区块。

## 七、没做到 / 不确定项（如实）

1. **内置 Ollama 适配器未做真实模型端到端实测**。本批只实测了它的**失败路径**（模型不可达 →
   `advisory=None` + `last_error`，不编造，见 §五.4）。**没有**对真实 Ollama 跑过一次
   成功的建议输出（依赖本机模型在线、且会引入非确定性，与"自检要可复现"冲突）。
   因此「真模型输出能被 `_parse_json_obj` 正确解析」这条**未经实测**，只做过解析函数的
   容错设计（去 ```json 围栏 + 兜底正则抠 `{...}`）。
2. **生产路径 `/api/ask` 里适配器拿不到问题原文**。`ask_service.envelope_from_result(result, kb_name)`
   签名里没有 question，`_ask_impl` 的返回体也不含 question；按文件隔离纪律本批不改 `api_server.py`，
   所以接线点拿不到题面，`attach_if_enabled` 会退回 `result.get("question")`（当前恒为空串）。
   影响：内置 Ollama 适配器在生产链路上会以一个空问题提问 → 建议质量无意义。
   **修法（一行，留给主控）**：`api_server.py:1273` 改成
   `result = envelope_from_result(result, ..., question=req.question)`（或直接在 result 里塞 `question`）。
   本批的自检是直接调 `envelope_from_result` / `attach_if_enabled(question=...)`，**绕过了这个缺口**，
   所以 §五 的 PASS **不能**证明生产链路的建议质量，只能证明"契约与红线成立"。
3. **云端适配器未实现**。需要 key、且要引第三方依赖或自己写 HTTP（可写但本批未做）。
   扩展点已留：`register_adapter()` / `set_active_adapter()`，`requires_key=True` 时无 key 自动不启用。
4. **`requires_key` 路径未实测**。代码里有这条判据（无 key → 不启用），但没有可用的云端适配器来触发它，
   属于"写了未验证"。
5. **`_leaks_into_answer()` 的短串阈值 4 是拍的**。`len(s) >= 4` 才判定泄漏，避免"设备"这种
   两字词在答案里到处出现造成误杀；代价是 1–3 字的候选文本泄漏拦不住（极端情况）。
   该阈值**无外部依据**，属工程取舍。
6. **`attach_if_enabled` 的"answer/hit 被篡改"闸门不可达**（当前实现里适配器根本改不到某个 result）；
   它作为未来的防御性断言留着，**未被任何测试触发**（我没为它造可达路径，因为那需要改函数签名）。
7. **并发/多进程安全未验证**：`model_advisory` 的注册表是进程内全局（`_ADAPTERS`/`_ACTIVE`），
   多线程下 `set_active_adapter` 与 `is_enabled` 无锁。默认关闭态不受影响；启用态若在多 worker 下
   由请求线程动态注册适配器，**未测**。（生产建议只在启动时注册一次。）
8. 未做真实浏览器/前端验证（本批按规格可不改前端）。
