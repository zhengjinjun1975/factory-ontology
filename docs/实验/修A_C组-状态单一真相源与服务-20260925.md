## 一、A1「当前生效本体」的落点与理由

**落点：`codes/config/active_ontology.json`（新增，运行态，已加 .gitignore）。**

选它而**不**复用「具名配置 / kbs.json」的理由：

1. `kbs.json` 的语义是「**全部** KB 的注册表」。把"哪个生效"塞进去，会让注册表多携带一份会话态，
   每次切库都要改整张表，并与并发建库互相覆盖；职责混淆、写入面更大。
2. `web/web_state.json` 是**前端(BFF)持有的展示态**（table/nt/lexicon），后端与前端各写各的，
   正是"三处状态不一致"的来源之一。
3. 独立小文件 = **单一写入点（建库/切库）+ 服务启动读取**，后端与 BFF 读同一份，谁都不再自存一份激活态。
   体积最小、并发最稳。

写入/读取点：

| 时机 | 动作 | 位置 |
|---|---|---|
| 建库成功 | 写入 | `api_server._set_active_kb()`（被 `ontology_build` / `ontology_confirm` / `ontology_self_onboard` 调用）|
| 切库 | 写入 | `POST /api/kb/active`；BFF `setCurrentKb()` |
| 服务启动 | 读取并记日志 | `api_server` 模块加载：`ACTIVE_AT_START = _read_active()` |
| 读取（真相源） | `_active_kb()` | 后端所有需"当前库"的端点；BFF `getCurrentKb()` 读**同一文件** |

> 后端仍同步维护 `web/web_state.json` 的展示字段（nt/lexicon/table）以兼容旧前端，但 **kb 字段以
> `active_ontology.json` 为准**。

## 四、C3 会话有效期与清理策略（如实说明）

C3 在**本次会话之前**已由 `web/server/auth.js` 实现（不是本轮新写），本轮**实测确认并纳入证据**：

- 存储：`web/sessions.json`（已 `.gitignore`），内存 `Map<token,{username,expires}>` 为热态。
- **有效期：12 小时**（`SESSION_TTL = 12*3600*1000`），签发时写 `expires`。
- 加载即清理：`loadSessions()`（启动 `restoreSessions()`）过滤掉 `expires <= now` 的条目。
- 使用即清理：`resolveUser()` 命中过期项即删除并回写磁盘。
- 写盘时机：`login` / `logout` / 过期命中各回写一次。
- **无周期性清扫线程**：过期项只在"下次加载/下次访问该 token"时被剔除。属可接受的惰性清理
  （文件仅随登录增长，且过期项会在下次加载时被清）。

## 六、没做到 / 不确定项（如实）

1. **`_kb_ontology_schema` 规则③（基础库例外）**：当 `kb == KB_NAME`（引擎默认基础库，默认 `food`）
   且无 per-kb schema 时，解析为仓库标准本体 `config/ontology_schema.json`。理由：这是**基础库自身的本体**，
   历史上就是标准合规/导出的对象，不是"拿别的库的本体冒充"。**仅对基础库生效**；任何**非基础库**找不到本体
   一律报错（自检用 chem 验证了这一点）。若评审认为这仍属"回落全局"，可改为给 `food` 在 kbs.json 显式声明
   schema —— 但那会触发 `_ensure_ontology` 重建 `output/food.nt`，有改动问答基线的风险，故未采用。
2. **BFF 门禁的"单企业收敛"语义**：BFF 每个业务请求都会 `setCurrentKb(user.kb)`。因此"当前激活库"实际
   跟随**登录企业绑定的 kb**。本轮已让 `confirm` / `self-onboard` / 行业切换同步更新 `user.kb`，使
   "建哪个激活哪个"成立；但若**只**通过后端 API 切库而不同步 `user.kb`，则下一次经 BFF 的请求会把激活态
   拉回该用户的 kb。这是既有产品语义（一企业一库），未改变；如需"纯后端切库也能压过用户绑定"，
   需另立规则（涉 B 组/B4 顶栏），本轮未做。
3. **A4 冲突校验的覆盖范围**：只在 `confirm` / `self-onboard`（真正写 `data_dir` 的建库路径）强制；
   `POST /api/ontology/build` 不写 `data_dir`，未加校验。既有注册表里 6 个 KB 共用 `data`（均为备案
   清理项 + `food_co`），按设计**不追溯拒绝**（清理项不参与占用判定），故现网无新增冲突。
4. **C1 代理鉴权**：`/api/standard/` 经 BFF 需登录（纳入门禁），与 `/api/ontology/*` 一致；未做"匿名可读"。
