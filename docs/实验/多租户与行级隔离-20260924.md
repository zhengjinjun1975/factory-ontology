## 1. 设计概览

### 1.1 租户模型（配置驱动，不写死）

`codes/config/tenants.json`：

```json
{ "default_tenant": "default",
  "tenants": {
    "default":  {"name": "默认租户(未启用多租户的既有部署)", "kbs": "*"},
    "tenant_a": {"name": "A企业", "kbs": ["valve"], "keys": ["<key>"], "role": "read"}
  } }
```

- `kbs` = `"*"`（全部，default 用）或 KB 白名单列表；`keys` = 该租户自带 API 凭据（凭据→租户声明）；`role` = 该凭据默认角色。
- **文件缺失/损坏 → 内置默认注册表（只有 default 租户、`kbs:"*"`）**，老部署行为逐字段不变。
- 运行时 `FOOD_TENANTS_FILE` 可指副本（自检用）；`FOOD_TENANT_COLUMN` 可改租户列名（默认 `tenant_id`）。

### 1.2 解析优先级（逐请求，无全局可变登录态）

凭据/令牌携带的 tenant 声明 → `X-Tenant-Id` 头 → 默认租户 `default`。
声明的租户不在注册表 → 403（`TenantUnknown`）；凭据声明与头**不一致** → 403（`TenantDenied`，不静默取其一）。令牌格式：`fotk1.<role>.<exp>.<sig>`（老，无租户）+ `fotk2.<role>.<tenant>.<exp>.<sig>`（多租户）。

### 1.3 上下文（线程安全，随请求生命周期）

`contextvars.ContextVar` + `TenantContext`（不可变）。API：`set_current/reset/current/current_id/require_current/tenant_scope`。
**不用任何模块级可变全局量**；`with tenant_scope(...)` 退出即还原（自检实测：两线程各见自己的租户、退出后无残留）。

### 1.4 隔离落点

| 层 | 落点 | 缺上下文时 |
|---|---|---|
| SQL 组装（单点） | `db_dialect.select_all_scoped / tenant_clause` | **抛 `TenantContextError`** |
| 数据读取 | `db_loader._read_sqlite`（PRAGMA 探测租户列）/ mysql / postgres | 带租户列且无上下文 → 抛错；无租户列的历史表 → 老行为 |
| KB 可见 | `tenant.kb_visible/require_kb` + `kb_registry.list_kbs/get_kb(tenant=)` | 未知租户 → 一律不可见 |
| HTTP 访问 | `api_server._kb_guard(kb)`（10 处 KB 端点，含 `_get_kb_ctx` 汇聚点） | 无租户上下文（库内直调）→ 不拦（向后兼容） |
| 审计 | `audit_chain._append` 必带 tenant；`_audit_event` JSONL 必带 tenant | 无上下文 → `default` |

## 6. 没做到 / 不确定项（据实列出）

1. **MySQL/PostgreSQL 行级隔离未做运行时验证**：驱动未安装（`pymysql`/`psycopg2` 缺失），无法起真库。代码路径已就位（`_read_mysql/_read_postgres` 在 cfg 声明 `tenant_col` 时走 `select_all_scoped`，缺上下文同样 fail-closed），但**只经代码审查，无实测证据**；且 mysql/pg 侧**不做列自动探测**（SQLite 用 PRAGMA 探测，mysql/pg 需配置显式 `tenant_col`）——这一不对称是**已知设计取舍，未验证**。
2. **`X-Tenant-Id` 头本身不鉴权**：认证端点里凭据声明优先、冲突即 403；但**无凭据的既有路由**（`/api/ontology/structure`、`/api/ontology/graph` 等，前次加固报告已记为 P1 信息暴露）仍可用 `X-Tenant-Id` 自行选租户。即「头部租户声明」在没有凭证时是**未经验证的声明**，本轮不修（加鉴权会破坏前端，见前报告 §5）。真实部署建议：这些路由前置网关鉴权，或只信凭据声明。
3. **`data_loader.py` 有一处未收口的 SQL 组装**（`codes/data_loader.py:57` 的 `SELECT * FROM "{table}"`，无租户条件）。它**不在本轮允许改动的文件范围**内，因此未动 —— 作为残留项登记（它读的是「库内已存在表」，非请求参数驱动）。
4. **`/api/stats` 的 tie 顺序既有非确定性**（`device_type_dist/status_dist` 等分组统计，计数相同时顺序随机，**同版本两进程 raw 结果即不同**：`raw_equal=False canon_equal=True`）。与本改动无关，但会影响「逐字段 ==」类断言，本轮对照改用**内容规范化口径**并额外证明该非确定性；若下一轮要「严格逐字段」，需先修引擎侧的排序稳定性。
5. **租户上下文在依赖里 `set_current` 未显式 reset**（靠 FastAPI 每请求任务上下文天然隔离；中间件侧有 `finally: reset`）。实测无跨请求泄漏（连续 A 请求后，无租户请求仍落 default），但这是**运行时行为验证**，非语言层保证；下一轮若出现跨租户串台，优先复查这里。
6. **default 租户等同超管**（`kbs:"*"` 可见全部 KB，含各租户私有 KB）。这是「老部署行为不变」的锚点，但**真实多租户部署必须收口 default 的 scope**（改 `tenants.json` 的 `kbs` 白名单）。本轮刻意保留。
7. **`probe_kb / dict_layers / merge_dict_layers / register_kb / unregister_kb` 未做租户过滤**（它们是注册表工具函数，非列表/访问端点）。`/api/ontology/build` 已加 KB 守卫，但直接调 `kb_registry.register_kb` 的脚本不受租户约束 —— 未验证、未加锁。
8. **`codes/config/tenants.json` 是新增配置文件**（不在任务给定的「允许新增」清单里，但「租户注册表读 config 不写死」必须有落点）；内容只有 default 租户，不改任何现有行为。若下游严格要求只允许清单内文件，可删除该文件 —— 缺失时 `tenant.py` 退化为内置默认（自检已覆盖该分支）。
