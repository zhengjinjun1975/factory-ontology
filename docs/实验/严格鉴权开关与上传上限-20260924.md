### 开关语义

- `FOOD_STRICT_AUTH` 取值 `1 / true / yes / on`（大小写不敏感、允许首尾空白）→ **开**；其余一切值或未设置 → **关**。
- **关（默认）= 现状不变**：中间件不进入鉴权分支，所有端点（含匿名访问本体结构与图端点）行为与 HEAD 一致（下面第 2 节有逐字段对照证据）。
- **开**：下列路径必须带凭据，否则 401；`/admin` 需 admin 角色，否则 403。

### 严格模式下受保护的端点

| 路径 | 所需角色 | 判定理由 |
|---|---|---|
| `/api/ontology/structure` | read/admin | 本体类/层级/对象属性 = 业务结构数据 |
| `/api/ontology/graph` | read/admin | 完整本体图（节点+边）= 业务数据 |
| `/api/ontology/graph-svg` | read/admin | 本体大图 SVG = 同一份业务数据 |
| `/api/app-config` | read/admin | 知识库品牌/示例问题 = 业务配置数据 |
| `/api/flows` | read/admin | 流程注册表状态 = 业务编排元数据 |
| `/api/flows/presets` | read/admin | 预设卡 = 业务编排配置 |
| `/metrics` | read/admin | 端点请求计数 = 运营情报（见下方决策） |
| `/admin` | **admin** | 管理后台页（管理面入口） |

## 二、`/health` 与 `/metrics` 的显式决策（及依据）

- **`/health` 保持匿名（严格模式下也不鉴权）。**
  依据：`/health` 是**运维探活**端点——k8s liveness/readiness、负载均衡健康检查、`verify_tenant.py`/
  `verify_strict_auth.py` 的 `wait_ready()` 都靠它无凭据探测（本轮两个自检脚本正是如此使用）。
  若给它加鉴权，探活方必须持凭据，会破坏标准探活契约、并可能让编排层误判实例不可用而反复重启。
  它只返回 `{"status":"ok","version":...}`，不含任何业务数据，泄露面可忽略。
- **`/metrics` 严格模式下要凭据（read 即可）。**
  依据：`/metrics` 返回的是各端点请求计数（端点路径清单 + 流量画像），属**运营情报/攻击面信息**，
  匿名暴露可为攻击者提供侦察便利，故严格模式下关闭匿名读取。取 **read** 而非 admin：监控/排障
  侧常持 read 凭据，要求 admin 属过度收紧且易误伤运维看板；read 已是受信内部主体。
  默认（关）时保持匿名不变（兼容既有监控）。

两处决策均已在 `verify_strict_auth.py` 第 3 节用**真实 HTTP** 断言（`/health` 匿名 200、
`/metrics` 匿名 401 且 read 200）。

## 三、上传体积上限

- 可配项：`FOOD_MAX_UPLOAD_MB`（浮点，MB）。**默认 50**（`MAX_UPLOAD_MB=50.0`，`MAX_UPLOAD_BYTES=52428800`）。
- 作用面：`POST /api/admin/upload`（CSV）与 `POST /api/knowledge/ingest`（PDF/Word/TXT）。
- 超限行为：**HTTP 413 且不落盘**（`admin_upload` 用 `HTTPException(413)`；`knowledge/ingest`
  用 413 + 既有信封体 `{ok:false,error:{code:4001,...}}`，便于前端沿用信封解析）。
- 读入方式：`_read_upload_capped()` 逐 1MB 分块 `await file.read(chunk)` 并累计，
  累计一旦超过上限立即抛 `UploadTooLarge` 中止——**不含任何 `await file.read()` 一次性全读**。

### 默认值 50MB 的取值依据

1. **不回归**：既有 `/api/knowledge/ingest` 在架构师审计（P1-5）时已定的文档上传上限就是 **50MB**；
   默认沿用同一值，则**原本能被接受的文档（≤50MB）依旧被接受**，本改动只把响应码从 200 信封
   改为 413（见「改动/不确定项」）。
2. **同口径**：`admin_upload` 原本**完全没有上限**（无界 `await file.read()`），把它对齐到文档入口
   同一上限，一处 env 同时管住两个入口。
3. **够用且保守**：工厂 CSV 真实数据在 MB 量级（`codes/data/*.csv` 最大的也只有几 MB），
   50MB 的 CSV 约合数百万行，远超单表规模；PDF 文档资料 50MB 亦属宽裕。上限同时充当内存上界
   （分块累计不超过 上限 + 1 块）。

### 「磁盘无残留」的证据口径

- `admin_upload`：超限时**先读后写**，`DATA` 目录前后 `listdir` 完全一致（未生成 `food_products.csv`）。
- `knowledge/ingest`：超限时在**创建临时文件之前**就返回，`FOOD_TMP_UPLOAD_DIR` 前后 `listdir` 均为空。
- 另查 `codes/output/_tmp_uploads`（未覆盖时的默认临时目录）亦无本用例残留。

## 五、没做到 / 不确定项（诚实清单）

1. **`/admin` HTML 在严格模式下无法用浏览器直接打开。**
   `/admin` 走的是「顶层导航」，浏览器不会带 `X-API-Key` 请求头；严格模式下它要求 admin 凭据 →
   浏览器直接访问会被 401。这是「给 HTML 页加头鉴权」的固有局限。**实际影响到的是：严格模式下
   必须由反向代理注入凭据（如反代校验后转发、或改造为 Cookie 鉴权）才能用浏览器打开管理页**。
   本轮按任务要求仍对 `/admin` 设为「必须带凭据 + admin 角色」；如后续需要浏览器可用，
   建议在第 3/4 轮的会话/Cookie 鉴权里一并解决。**风险：不改则管理页在严格模式下对浏览器不可用。**
2. **未对 `/`（落地页 HTML）设限。**
   依据：它只是「当前 kb 品牌 + 示例问题 + 跳转 3001」的静态外壳，不含任何业务记录；
   且它是统一入口页，设限会让严格模式下整站入口失效。**被绕过的风险**：匿名者可读到
   「当前激活的是哪个 kb / 品牌名 / 示例问题」这点弱信息。判定为可接受。
3. **`/api/kbs`、`/api/stats`、`/api/ask` 等早已鉴权**（`require_key`），本轮无需处理；
   但**任何新增的匿名只读路由**今后都可能绕过本开关——本开关是**路径白名单**（默认只保护上面 8 条），
   不是「默认全保护」。**风险**：以后新增匿名业务端点时若忘了加进 `_STRICT_READ_PATHS`，
   严格模式也保护不到。已在代码注释里点明该清单的位置，建议纳入评审检查项。
4. **`knowledge/ingest` 超限的响应码由 200(信封 code=4001) 改为 413**——这是本轮有意为之
   （任务要求「超限返回 413」）。若历史上有前端按「HTTP 200 + code=4001」解析该错误，
   需相应适配；已尽量保留信封体结构以降低适配成本。此变动在**默认模式下也生效**（体积上限本身
   与鉴权开关无关）。**不确定项**：我未逐一排查 `web/` 前端是否有人依赖旧的 200 信封写法。
5. **超大 body 的 ASGI 层 spool**：FastAPI/Starlette 在进入端点前会先把请求体落到
   `SpooledTemporaryFile`（>1MB 溢出到 `%TEMP%`）。我在端点内做的是**有界分块读入**
   （不一次性 `read()`、超限即停、我们自己的目录不留文件）；但**Starlette 这一层的落盘不在本改动
   可控范围**，它由框架行为决定、且会自行清理。**没做到**：从 ASGI 入口就用地道的流式拒绝
   （需要在更底层改写请求体处理，超出「纯标准库 + 单文件改动」的范围）。若要求「连框架临时文件都不落盘」，
   需另开一轮做自定义 ASGI 中间件（并注意：过早关连接会让客户端拿不到 413 响应体——我实测过在中间件里
   Content-Length 早拒，客户端会收到 `ConnectionResetError`，无法读取 413 body，故本方案未采用该做法）。
6. **值 `2`/`enable` 等「类真值」被判为关**（只认 `1/true/yes/on`）。这是任务给定的语义，已用真实函数断言。
   若运维同学误写 `FOOD_STRICT_AUTH=enable`，会静默保持「关」。**风险**：开关静默不生效。
   目前无启动日志提示开关状态——**没做到**：未加「启动时打印 STRICT_AUTH 状态」的 INFO 日志
   （担心改动面扩大；如需要可补一行 logger.info）。
7. **`_strict_auth_check` 按「路径」而非「路由」判定，且已 `rstrip('/')` 归一**。
   `/api/ontology/structure/`（带尾斜杠）会被 `rstrip` 后匹配；但 `/admin/` 归一为 `/admin`。
   未覆盖大小写变体（FastAPI 路径本身大小写敏感，不存在该问题）。列为已知实现细节。
8. 本轮的**并发**场景（同一进程内 `STRICT_AUTH` 是模块级常量，请求间不会变化）无需专门锁；
   未做并发压测——非本轮范围。
