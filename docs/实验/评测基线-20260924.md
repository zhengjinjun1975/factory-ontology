## 0. 一句话结论

在 8 个行业 KB、共 **331 问**（可答题 250 + 无答案题 81）上，评测的
**问答核心 `ontology_qa_v3.answer` 命中率 56.8%（142/250）**，未命中 13.6%（34/250），

## 1. 方法

### 1.1 被测入口（直接 import，未启 HTTP）

| 步骤 | 调用 | 说明 |
|---|---|---|
| 词典 | `ontology_qa_v3.load_dict(config/lexicon_<kb>.json)` | 自动并入公共工业词典 |
| 本体 | `ontology_qa_v3.parse_nt(codes/output/<kb>.nt)` | N-Triples → 三元组 |
| 数据 | `ontology_qa_v3.build_data(triples, D)` | → `{实例名: {属性: 值}}` |
| 问答 | `ontology_qa_v3.answer(question, data, D)` | **被测函数** |

选择理由：`ask_service.py` 承载 `/api/ask` 的**无状态融合层**（证据归一化 / LLM 润色 / 文档 RAG 融合），
其本身不产生答案；真正的确定性问答核心在 `ontology_qa_v3.answer`。
`run.py` 的 `ask()` 也只是 `answer()` 之后再叠加 GraphRAG/BM25/向量兜底。
**本批不起 `api_server` HTTP 服务**（任务要求），故直接以 in-process 方式调 `answer()`——
即"规则+本体"这一确定性地基。线上端到端口径的差异见 §6。

**未纳入本基线的层**：`api_server` 的 LLM 润色、文档 RAG 融合（`_fuse_doc_supplement`）、
GraphRAG/BM25/向量兜底、多模型兜底。这些层**可能**在线上提高命中，需另建 HTTP 口径基线才能对比。

### 1.2 评测集构成（五类问法）

评测集由 `scripts/eval_qa.py --gen` **确定性**生成（golden 全部由真实 CSV 算出，零人工标注、
不调模型），落盘为固定 fixture：`codes/tests/fixtures/qa_eval/<kb>.json`。

| 类别 | 代号 | 含义 | 判分方式 |
|---|---|---|---|
| 普通属性问 | `attr` | 计数 / 极值 / 均值 / 枚举（如"产品中价格最大是多少"） | 数字命中 / 枚举全含 |
| 类型词作主语 | `type` | "<X>的类型有哪些""<X>的类型有多少种"（如"设备类型有哪些"） | 枚举全含 / 数字 |
| 多实体 / 多表 | `multi` | 库内第二个实体计数、跨表关联（如"B001 批次用了多少种原料"） | 数字 |
| 否定或比较 | `neg` | 最小极值、区间（"…大于 N 的有多少"）、按枚举值过滤（含反作弊 absent 名单） | 数字 / 全含且不含他值 |
| 无答案（库里没有的东西） | `noans` | 问库中不存在的实体/属性（如"有多少个客户""<X>中纯度最大是多少"） | 期望拒绝 |

**无答案类的假概念已逐一核验**：8 个 KB 的每个假实体/假属性都确认**不出现在该 KB 的任意 CSV 取值中**
（脚本核验：`fake_ent命中数据=[] fake_attr命中数据=[]`），因此"引擎给出具体值"确为编造，非误判。

### 1.3 判分口径（未命中 ≠ 误答 ≠ 编造，三者分列）

有答案类（250 题）：
- **hit 命中**：答案含 golden 事实（数字按独立数字匹配、±1% 容差；枚举要求全含）。
- **miss 未命中**：引擎拒答（命中 `暂不支持/未找到/无相关数据/不含所问…`）——诚实但答不出。
- **wrong 误答**：引擎给了具体答案，但事实错误（**有答案但答错**）。

无答案类（81 题）：
- **refuse_ok 正确拒绝**：命中拒答话术。
- **fabricate 编造**：断言了库中不存在的具体事实（出现了非零数字 / 具体实体）。
- **empty_zero 空答**：返回具体 "0/N" 空答（如"客户总数 0"）——既非明确拒答，也非明确编造，**单独计数**，
  不计入编造。该桶是启发式（"答案中数字是否全为 0"），边界存在个案争议，见 §6。

**从数字可读出的真实差距**（样例取自终端 stdout，详见 §5）：
- **计数被词典映射带偏**：`energy_station/manufacturing/chem` 的"有多少台设备/有多少个产品"被答成 **0**——
  词典 `entity_cn2en` 把"设备/产品"映射到了本库**不存在**的类名（如 chem 映射到 `mach_*`、energy_station 无实体映射），
  本体里的类（`Energy_station`/`Chem_products`）对不上 → 计数归零。这是**误答**（不是拒答）。
- **区间/过滤被"实体总数"抢答**：ai4i "空气温度大于300的机器有多少" 返回 `有 10000 个机器`（全库总数），
  valve/auto_parts/food 同样，"大于 N"一律回总数 → **误答率高企**。
- **词典枚举与真实列错位**：valve "压力等级有多少种" 返回 `共有 6 种类型`（其实是产品类型数），
  多种"有多少种"都答成产品类型数 → 误答。
- **属性名未对齐时静默串味**：library "借阅量最大是多少" 用**库存**的值回答（借阅量列未进词典）→ 误答；
  无答案类里"纯度/页数最大是多少"也被别的属性抢答 → **编造**。
- **无答案类大量"空答 0"**：41/81 是"X总数 0"式空答，属**未明确拒绝**——体验上比"编造"轻，但同样不达"诚实拒答"标准。

> 说明：跳过的库多为**有数据但未建本体**（A 类），属"数据在、本体缺"的存量缺口，

## 6. 我无法确认的地方 / 口径局限（务必与数字一起看）

1. **与线上端到端的差异**：本基线只测 `ontology_qa_v3.answer`（规则+本体地基），
   **未测** `api_server` 的 LLM 润色、文档 RAG 融合、GraphRAG/BM25/向量兜底、多模型兜底（因不启 HTTP）。
   线上 `/api/ask` 的实际命中率**可能高于**本基线，需另建 HTTP 口径基线方能对比；两者不可直接混用。
2. **nt 与 CSV 的字段级一致性未逐字段核对**：已验证 8 个 KB 的 `parse_nt` 实体数 **等于** CSV 行数
   （10/11/68/142/24/10000/10/48），但**未逐字段比对** nt 属性值与 CSV 单元格，
   不排除个别字段级陈旧。golden 取自 CSV，故若 nt 陈旧会压低命中。
3. **判分是确定性字符串/数字匹配，不做语义等价**：答案表述正确但形式不同（换行、别名、四舍五入方式）
   可能被判误答；反之 golden 数字偶然出现在无关文本中也可能被判命中。误差方向未量化。
4. **"编造 vs 空答"边界是启发式**：以"答案中数字是否全为 0"区分空答与编造。
   例如"客户总数 0"记为**空答**（未明确拒绝，也非明确编造）——若你认为"答 0"也算编造，
   则编造数应为 4+41=45 而非 4。此边界**建议由主控拍定口径**，我按"更保守、不冤枉"的方式分类。
5. **baseline 受词典质量强烈影响**：多个 KB 的 `entity_cn2en`/`attr_cn2en` 与本体类名/数据列不对齐
   （chem 指向 `mach_*`、manufacturing 含表中不存在的 `contract_no` 等），这类"词典离位"本身是**引擎侧真实缺陷**，
   但也意味着：**改词典即可显著改变本基线**——这是特性还是噪音，取决于后续改造是否把词典对齐纳入范围。
6. **单表 KB 的"多实体/多表"类不等价**：energy_station/ai4i/library 只有一张表，
   其 `multi` 类用"类型值过滤计数"组合题代替真正的跨表关联题，与多表 KB 的 `multi` 不完全同质。
7. **仅测准确率，未测时延/并发**：基线不含 p50/p95、并发压测。
8. **问法为脚本生成，覆盖五类但非穷尽真实问法**：各类在某 KB 的题量上限被裁剪（attr≤16/neg≤12/…），
   保证五类可比，但与真实用户分布不必然一致。
9. **引擎存在输出顺序的非确定性**：并列实体/并列极值场景下，引擎用集合迭代输出，
   同一问题两次运行的**名单顺序会变**（指标不变）。故基线 JSON 只存计数、不存原始答案文本，
   以保证"量尺"字节可复现；样例文本仅作示意。

## 7. 下一步建议（不在本批范围）

- **P0 误答**：修"区间/过滤被实体总数抢答"（ai4i/valve/food/auto_parts）、"词典实体映射指向不存在类导致计数归零"（energy_station/manufacturing/chem）。
- **P0 编造**：属性名未对齐时的静默串味（library 借阅量→库存、无答案的"纯度/页数"被别的属性抢答）应改为**明确拒答**。
- **P1**：把"空答 0"（41 条）改为明确拒答话术，从"未明确拒绝"升级为"诚实拒绝"。
- 每次改造后重跑 `python scripts/eval_qa.py --out scripts/eval_qa_baseline.json`，与本基线 diff 计数即可量化进退。
